PrescribeX audit pipeline: architecture, knowledge base and retrieval

Fixed clinical rules raise possible mistakes, using facts looked up from a 100,000-fact knowledge base. A local language model then confirms or rejects each one. It is never allowed to invent a new mistake.

Explanation of each step

The nine steps in the order they happen. Step numbers match Diagram 1.

1

The doctor saves a section

The app has six audited sections: Chief Complaint, Past History, Investigation, Diagnosis, Rx (medicines) and Advice. Every save does two things:

  • It writes a JSON file to backend/data/patient_x/visit_NN/ and updates the Excel workbook (Patient Info, Prescription Data, Prescription Log).
  • It starts a live audit for that section.

Each live audit has a revision number. If the doctor edits the section again before the answer arrives, the older answer is thrown away.

App.jsxbackendPlugin.jsdatabase.js
2

The request reaches the Python bridge

The browser calls /audit-api/audit/section. Vite forwards it to the Python server on port 8765 and waits up to 5 minutes. The server runs at most 2 audits at once, so a slow model does not pile up requests.

vite.config.jsapp_server.py
3

The adapter flattens the visit

The app saves structured data. The adapter turns it into one flat row of text, for example Napa 500 mg (1 + 0 + 1) - (5 day(s)). It also turns a date of birth into an age such as "8 months", converts Bangla digits and fixes dose fractions.

For a live audit it keeps only the fields that section is allowed to see. Chief Complaint, Past History and Diagnosis do not load earlier visits. Investigation, Rx and Advice build a small temporary database of the patient's earlier visits, so the engine can spot repeats and interactions.

app_adapter.pyincremental_audit.py
4

The 14-stage engine raises candidates

A candidate means "this might be a mistake". Examples are Rx.ddi (drug interaction), Rx.over (too much medicine) and Adv.refer (referral missing). The rulebook has 53 rule IDs across Demo, CC (chief complaint), Hx (history), Dx (diagnosis), Inv (investigation), Rx and Adv.

Everything here is fixed code with no AI. Weak, low-evidence candidates are dropped before the model sees them. The result is one compact task per section.

Because the model only sees what the rules raise, the rules decide how many real errors can be caught (recall). The model's job is to remove false alarms (precision).
orchestrator.pyrule_candidate_engine.pysafety_candidate_engine.pyprotocol.yaml
5

The local AI model reviews each candidate

The prompt tells the model to review only the given candidates, never invent new ones, answer only in JSON, keep each reason under 25 words and avoid direct treatment orders. Candidates with the same evidence are grouped so the model reads that text once. If the answer is not valid JSON, the writer retries with a repair note.

The model is chosen in .env and loaded once into GPU memory. Two prompt styles exist:

  • Standard: "confirm or reject each candidate".
  • Fine-tune: ask the model, in the format it was trained on, which rules apply, then map its answer back to the candidates. For CC and Hx it also asks plain YES/NO questions.
audit_writer.pyprovider.pyfinetune_prompt.py
6

Clean-up of the model's answer

This protects the doctor from noise. The pipeline drops answers that:

  • only repeat the candidate's own wording, or are too short to be a real reason;
  • say in their own text that nothing is wrong ("no issue", "plausible");
  • are duplicates, or known double-fires of the same fact (for example CC.context.demo and CC.context.conflict), where only the most severe is kept.

Wording is also softened into review language. The report builder then drops any finding with a missing field or no evidence, and records a warning for each drop.

audit_writer.pyfinal_report.py
7

The badge on the section

Findings are sorted by severity and at most 5 are shown, to avoid alert fatigue. The badge is one of:

  • Clear: nothing found.
  • Moderate: concerns that need review.
  • Critical: at least one major or critical finding.
  • Error: the model could not complete the check; the doctor can retry from the badge.

Patient-context notes, such as pregnancy evidence on a male patient, appear as "possible errors" on the Chief Complaint badge. Results are also saved to the Excel Prescription Log.

incremental_audit.pySectionAuditBadge
8

The final audit

"Run audit" calls /audit and runs all 14 stages over the whole prescription, including the optional search planner. It then compares the live findings with the final ones and lists any difference instead of hiding it. The full report is saved as aiAudit.json in the visit folder.

app_server.pycompare_live_with_final
9

The benchmark (a separate tool)

benchmark/run_benchmark.py replays synthetic prescriptions section by section, exactly as the app does, with 16 local models plus a "rules-only" baseline that uses no AI. Each model runs in its own process. It scores:

  • Precision: how many warnings were real.
  • Recall: how many planted errors were caught.
  • Speed and memory: seconds per case, tokens per second, GPU memory.

The top 5 models were then set up for a second test on doctor-annotated real prescriptions (branch real-prescription-eval); only sample data has been run so far.

run_benchmark.pymodels.jsonexport_doctor_review.py

Retrieval: how facts are found

Is FAISS used? No. Are embeddings used? No.

I searched every file in audit_pipeline/ and benchmark/ for faiss, sentence-transformers, embedding, bm25, tfidf, chroma, vector, cosine, numpy and sklearn. The only hit was the word "embedding" inside a comment in text_translation.py. The Python environment has no faiss, sentence-transformers, rank_bm25, scikit-learn or peft package installed. numpy is present only because torch needs it.

The name "RAG" is used in the code (guideline_rag.py), but the lookup is a dictionary lookup with hand-written scoring. Nothing is converted into numbers and nothing is compared by similarity.

How GuidelineRAG works, step by step

a

Load everything into memory at start

The whole 97 MB file is read with read_text().splitlines() and every line is parsed. No database and no index file on disk. This happens once, the first time an audit needs it.

b

Build a name dictionary

For each fact, these words become dictionary keys pointing to that fact: condition, condition_aliases, medicine_name, generic_name, the recommended, alternative and avoid medicines, and drug_class. Text is normalized first, and two stop lists (ALIAS_STOPWORDS, NON_CONDITION_ALIASES) remove words too general to be useful.

c

Find names inside the patient text

Diagnosis, chief complaint, clinical text and the medicine list are normalized. Each key is searched inside that text as a whole phrase (phrase_in_text). A fact matches only if its key appears as an exact phrase. For Diagnosis and Investigation, a match on a medicine name alone is ignored.

d

Score every matched fact

A whole-number score is added up from the table below. Facts with a category mismatch score 0, and context_only facts score 0 unless asked for. Storage facts are excluded.

e

Sort and cut

Sort by highest score, then source priority, then source id, then fact type. Keep only the first few (limit 3 to 4 per question). Duplicates (same fact_id) are removed per section.

The textbook fallback (Diagnosis and Investigation only)

If no exact condition is found, _add_textbook_symptom_candidates compares the patient's symptom words with textbook facts. It needs at least 2 shared symptom words. Score: 35 + min(overlap, 5) × 8, plus 20 if the fact is meant for this section, minus 15 if it is not. This is still word overlap, not meaning similarity.

Good and weak sides of this design

Strengths
  • Same input always gives the same facts. Easy to test and to explain.
  • No GPU, no embedding model, no index to keep up to date.
  • Every fact has a source id and page, so a warning can be traced back.
  • Local Bangladesh guidance outranks textbooks by design.
Weaknesses
  • A synonym, abbreviation or misspelling that is not in the alias list is missed. There is no fuzzy or meaning-based match.
  • The 97 MB file is parsed at every server start. I did not measure how long this takes.
  • The default path is relative (audit_pipeline/data/rag/...), so it only works when the server starts in the project root. Otherwise the facts are silently empty, with only a warning "guideline RAG file not found or empty".
  • Score weights are untuned.
If asked "why not FAISS?": exact matching was a safe first choice because medicine and condition names are mostly fixed terms. A later improvement could add FAISS with an embedding model as a second layer that only adds recall when the exact match finds nothing. That is a suggestion; it is not built and I have not tested it.

Medicine mapping: how a written name becomes a drug

MedicineMapper.map_one tries these tiers in order and stops at the first that works. Every tier is an exact, normalized-name comparison.

TierWhat it checksResult label
1. AliasIs it a listed supportive item (ORS, oxygen, vaccine, amoxiclav...)?from medicine_aliases.yaml
2. Inferred combinationDoes the name safely split into known generics?combination result
3. Exact genericIs the head of the text a generic name?match_confidence = exact, reason "exact generic match"
4. Exact brandIs it a brand in medicine.csv? Chooses the best strength/form variant.brand row. A solid-tablet prescription is not compared to a liquid-only brand row if a solid generic variant exists
5. Inferred genericSafe inference from the written textinferred
6. UnmatchedNothing safe foundmatched = false, "no exact or safe inferred match"

Text such as Napa 500 mg (1 + 0 + 1) - (5 day(s)) is first split into medicines (commas, semicolons and new lines outside brackets). The dose in brackets is read by frequency_parser.py, which understands Bangla, Arabic and Persian digits and fractions. It then calculates the daily dose conservatively. A medicine with no match gets no drug facts, which produces the warning "missing generic_id; no medicine facts retrieved".

Known gaps in the rule engine

From the benchmark notes: these cases raise no candidate at all, so the AI model never sees them: clarithromycin with simvastatin, tramadol with an SSRI, nitrate with a PDE5 inhibitor, PPI duplication, daily methotrexate, amiodarone in breastfeeding, weight-based paracetamol overdose in infants, NSAID in chronic kidney disease, benzodiazepines in the elderly, and antibiotics for viral illness.

The AI reviewer: prompts, providers and clean-up

What the model is asked to do

audit_writer.build_audit_prompt builds one prompt per section. It contains the instructions, the compact task (TASK_JSON), and the exact answer shape (REQUIRED_JSON_SKELETON). The chief-complaint section has its own wording, and Past History, Rx, Advice and the pregnancy-danger check have extra blocks. The model must answer in JSON and may only refer to candidates already in the task.

Prompt size control. Several narrow candidates from one complaint line often share the same evidence text. _group_candidates_for_prompt groups them into one entry {"evidence": ..., "checks": [...]} so the evidence is written once. This changes only how the prompt looks. Matching back to candidates always uses the original ungrouped list, so every check keeps its own candidate_id and rule_id.

Answer size. max_tokens = min(max(base, 140 × number_of_candidates + 120), 3000), where base is 650 live and 1000 final. If the JSON is invalid the call is retried with a REPAIR instruction (1 retry live, 2 final).

The live view shows the top 5 findings (LIVE_AUDIT_MAX_FINDINGS), sorted by concern level, then confidence. Statuses are clear, moderate, critical, or error (a partly failed run counts as error). "Possible errors" from patient-context warnings appear only on the chief-complaint section.

Fine-tune mode

A fine-tuned model was trained on a fixed prompt format, so finetune_prompt.py rebuilds that format from configs/finetune_taxonomy.json. The model lists detected_errors, and the code maps each one back to a rule candidate. For some rules it instead asks a short YES/NO question (for example "Is this entry an unrecognizable, misspelled or non-existent medical term?"), by default for CC.2, CC.4, CC.term.unclear, CC.context.conflict, Hx.term.unclear, Hx.context.conflict (FINETUNE_QUESTION_RULES). An error type the model produces that has no candidate is handled by FINETUNE_UNSUPPORTED: confirm_high (default), omit, or confirm.

Benchmark: how models were compared

benchmark/run_benchmark.py runs one process per model so GPU memory is freed between models. It plays each test prescription section by section like a doctor would (live), then runs the final audit.

10hand-made test cases, 11 planted errors (8 critical, 3 major)
35larger synthetic set: 29 with errors, 6 clean
16 + 1models in models.json, plus the rules-only baseline

How a finding is scored: it counts as correct if it matches a planted error by rule ID prefix and keywords (matches()). Precision = correct findings ÷ all findings. Recall = planted errors found ÷ planted errors. F1 combines both. Critical recall looks only at the critical errors. Live recall looks only at the live (per-section) pass. Also recorded: seconds per case, tokens per second, LLM error rate, peak GPU memory and load time.

Read these numbers carefully.
  • There are only 11 planted errors, so one miss moves recall by about 9 points. Differences of a few points between models are not reliable.
  • Precision counts every finding that does not match a planted error as wrong, even if it is a real problem that was not planted. That is why every model, including the rules-only baseline, has low precision.
  • These results were produced before the later fixes (prompt grouping, alert filter, overlap table, quantization auto-detect) and before the current Gemma merged model. The project notes say not to treat them as current. A re-run is still to be done.
  • The fine-tuned model prescription13864/gemma-4-12b-prescription-audit is not in this table. In one manual test it missed a male/pregnancy mismatch that the base Gemma-4-12B and a Groq Qwen model caught. Precision and recall for it are unmeasured.
