PrescribeX pipeline, explained

How one prescription goes from the doctor's screen to an AI-checked warning badge. Written from reading the code in Local_pip on 8 Nov 2026.

The idea in one paragraph. The doctor fills in a prescription one section at a time. After each section is saved, fixed rules look for things that might be mistakes (for example, a drug that is unsafe in pregnancy). These "might be mistakes" are called candidates. A local AI model then reads each candidate with the patient's facts and decides: confirm it or reject it. The model is not allowed to invent new mistakes. A final audit repeats this for the whole prescription when the doctor presses "Run audit".

1. The big picture

2. Step by step

1

The doctor saves a section

The app has six audited sections: Chief Complaint, Past History, Investigation, Diagnosis, Rx (medicines) and Advice. Every save does two things:

  • Writes a JSON file to prescribex-app/backend/data/patient_x/visit_NN/ and updates the Excel workbook (sheets: Patient Info, Prescription Data, Prescription Log).
  • Starts a live audit for that section.

Each live audit gets a revision number. If the doctor edits the section again before the answer arrives, the older answer is thrown away.

2

The request reaches the Python bridge

The browser calls /audit-api/audit/section. Vite forwards it to audit_pipeline.app_server on port 8765 (it waits up to 5 minutes). The server allows at most 2 audits at once, so a slow model does not pile up requests.

3

The adapter flattens the visit

app_adapter.py turns the app's structured data into one flat row of text, for example Napa 500 mg (1 + 0 + 1) - (5 day(s)). It also turns the date of birth into an age string such as "8 months", converts Bangla digits, and fixes dose fractions.

For a live audit it keeps only the fields that section is allowed to see (defined in incremental_audit.py). Chief Complaint, Past History and Diagnosis do not load earlier visits. The other sections build a small temporary database of the patient's earlier visits so the engine can spot repeats and interactions.

4

The 14-stage engine

This is orchestrator.py. It is the heart of the project. Everything in it is fixed code with no AI, apart from the optional search planner in stage 6.

BandWhat happens, in plain words
A. Understand (1–5)Tidy the field names, pull out symptoms and exam findings, translate Bangla hints, build the patient profile (age, pregnancy, kidney or liver problems, allergies) and match brand names such as "Napa" to the generic drug (paracetamol). Matching is exact, never fuzzy guessing.
B. Fetch knowledge (6–8)Look up facts about each medicine and relevant guideline text from data/rag/*.jsonl. "RAG" only means "search a library, then hand the found text to the checker". Stages 7 and 8 run at the same time.
C. Candidates (9–12)Safety rules check dose, allergy, pregnancy and organ problems. Follow-up rules compare against earlier visits. The rule engine merges everything into candidates with IDs such as Rx.ddi (drug interaction), Rx.over (too much), Adv.refer (referral missing). Weak, low-evidence candidates are dropped. Finally one small task is built per section.
D. Model and report (13–14)The model judges the candidates. The report builder checks every field, removes duplicates and sorts by section.

The rulebook is configs/protocol.yaml (version V.21). It lists about 50 rule IDs across Demo, CC (chief complaint), Hx (history), Dx (diagnosis), Inv (investigation), Rx and Adv.

5

The AI model reviews the candidates

For each section, audit_writer.py builds a prompt that says: review only these candidates, do not invent new ones, answer only in JSON, keep each reason under 25 words, and do not give treatment orders. Candidates that share the same evidence are grouped so the model reads that text once.

If the answer is not valid JSON, the writer retries with a repair note (1 retry in a live audit, 2 in the final audit). A live audit also limits the answer to 650 tokens so it stays quick.

Which model? Your .env has AUDIT_PROVIDER=local and HF_MODEL pointing at a merged fine-tune folder under LLM_Trainer/outputs/...gemma-4-12B...knowledge_v1/merged, with HF_QUANT=4bit. The code supports two prompt styles:

  • Standard: "confirm or reject each candidate."
  • Fine-tune: ask the model in its training format which rules apply, then map the answer back to candidates. For CC and Hx it also asks extra plain YES/NO questions.

The style is chosen automatically if the model folder contains training_config.json. I did not check your folder, so I cannot say which style is active right now.

6

Clean-up of the model's answer

_normalize_findings in audit_writer.py protects the doctor from noise. It drops:

  • answers that only repeat the candidate's own wording;
  • answers whose own text says "no issue" or "plausible";
  • answers that are too short to be a reason (under 5 words);
  • duplicates, and known double-fires such as CC.context.demo and CC.context.conflict (only the most severe is kept).

It also replaces unsafe wording with neutral review language. final_report.py then drops any finding with a missing field or no evidence, and records a warning for each drop.

7

The badge on the section

summarize_live_report sorts findings by severity and shows at most 5 (to avoid "alert fatigue"). The status is one of: clear, moderate, critical (a major or critical finding) or error (the model failed). Patient-context notes, such as pregnancy evidence on a male patient, appear as "possible errors" on the Chief Complaint badge. The result is also saved to the Excel Prescription Log.

8

The final audit

"Run audit" calls /audit. It runs all 14 stages over the whole prescription, including the optional search planner. It then compares the live findings with the final ones and lists any difference instead of hiding it. The full report is saved as aiAudit.json in the visit folder.

9

The benchmark (a separate tool)

benchmark/run_benchmark.py replays fake prescriptions section by section, exactly as the app does, with 16 local models plus a "rules-only" baseline (no AI). Each model runs in its own process. It scores precision (how many warnings were real), recall (how many planted errors were caught), time, speed and memory. The top 5 models were then set up to be re-tested on doctor-annotated real prescriptions (branch real-prescription-eval); only sample data has been run so far.

4. Things worth checking

  1. Old benchmark numbers. CLAUDE.md says the 16-model results were produced before the latest fixes. Do not present them as current.
  2. Recall ceiling. The model can only judge what the rules raise. PROJECT_CONTEXT lists mistakes the engine never raises, such as clarithromycin with simvastatin, NSAIDs in kidney disease and daily methotrexate.
  3. Incomplete requirements.txt. It lists 3 packages. A local run also needs torch, transformers, accelerate, bitsandbytes and openpyxl. Using HF_ADAPTER needs peft, which your notes say is not installed.
  4. Privacy depends on one setting. "No patient data leaves the machine" is true only while AUDIT_PROVIDER=local. Your .env also holds Groq settings; switching to them sends prescription text to the cloud.
  5. Git state. You are on real-prescription-eval, not main. Six files show as modified and CLAUDE.md is untracked. The very large line counts in the diff may be line-ending changes only; I did not verify that.
  6. Past History rules. section_order in protocol.yaml omits Hx, though Hx rules exist and the app audits Past History. Probably fine, but I did not confirm how Hx tasks are built.
  7. Speed. Benchmark times ranged from about 80 to 600 seconds per prescription across models. Your notes say there is no batching or cache reuse, and the GPU sits near 50% use.
  8. Fine-tune quality. CLAUDE.md reports that your fine-tune missed a gender/pregnancy mismatch that the base model caught. That is still open.
  9. Small leftovers. A temporary diagnostic print in incremental_audit.py; a stale docstring in app_server.py that mentions Azure; a warning message that points to README_BRIDGE.md, which is not in the folder.
